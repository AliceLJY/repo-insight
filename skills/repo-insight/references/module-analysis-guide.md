# 模块分析指南

## 核心方法

按**业务功能**划分模块，不按文件或目录。一个逻辑模块可能跨越多个文件，一个文件也可能包含多个模块的部分实现。

分析深度标准：**交给另一个 AI 能仅凭报告复现系统的设计**。

## 全局视角要求

每个模块的分析都必须回答两个全局问题：

1. **在整个项目中的角色**：为什么存在？去掉它系统会怎样？
2. **与其他模块的设计协同**：和其他模块的契约是什么？协作模式是否与项目整体设计哲学一致？

孤立分析模块是最常见的错误。一个模块的设计选择往往是被其他模块的约束所驱动的。

## 模块分析四要素

每个核心模块必须覆盖以下四要素：

1. **核心数据结构** — 关键接口/类型定义（只贴理解设计必需的）
2. **执行流程** — Mermaid 时序图描述调用链，标注源文件路径和行号
3. **设计决策** — 为什么选这个方案，权衡了什么
4. **模块间依赖** — 谁调用谁，数据怎么流转，共享了什么状态

检验标准：如果另一个 AI 只读你的分析（不看源码），能否画出这个模块的架构图并解释工作原理？

## 模块识别方法

1. **业务功能角度** — 项目提供哪些核心业务能力？
2. **数据流角度** — 数据从输入到输出经过哪些转换阶段？
3. **职责角度** — 业务需求变化时，哪些代码需要一起改？

## 分析深度分级

- **核心模块**（创新点、架构关键组件）：设计思路讲透、核心流程有图有解读、设计决策解释权衡、协作关系画清楚
- **次要模块**（工具函数、标准封装）：一句话职责 + 文件路径 + 特别之处

## Subagent 并行分析

阶段 6 使用 Agent 工具为每个核心模块启动独立 subagent 并行分析。

### 调度策略

- 每个核心模块 → 一个独立 Agent subagent（`subagent_type: "general-purpose"`）
- 所有次要模块 → 合并到一个 Agent subagent 批量处理
- 所有 subagent 在同一消息中并行启动

### Subagent 协作规范

- **只分析分配的文件**，不越界
- **跨模块推断用【待主 agent 验证】标注**，主 agent 在阶段 7 交叉验证
- **深度优先于广度**，宁可把一个核心流程讲透
- **全局视角**，将模块放在项目整体语境中分析
- **叙事衔接**，草稿开头 1-2 句连接前一模块，结尾 1 句铺垫下一模块

## 覆盖率计算规则

- 覆盖率 = 通过 Read 工具实际请求过的行范围之并集 / 文件总行数
- 大文件（>500 行）必须分段读取，确保关键段落被覆盖：
  - 文件头部的类型定义和导入（前 100 行）
  - 核心业务逻辑函数
  - 文件尾部的导出/测试（如有）
- 只读了文件 <30% 不计入覆盖率，视为「未读」
- 自动生成代码（proto 生成、lock 文件等）可降低覆盖率要求

## 质量检查清单

- [ ] 模块按业务功能划分，不是按文件/目录
- [ ] 每个模块解释了"在项目中的角色"和"为什么这样设计"
- [ ] 四要素完整：核心数据结构、执行流程（含路径行号）、设计决策、模块间依赖
- [ ] 核心流程用 Mermaid 图展示
- [ ] 没有暴露不必要的函数名、参数名、类型定义
- [ ] 每个模块分析都连接到项目整体设计哲学
- [ ] 检验：另一个 AI 只读分析能画出模块架构图
